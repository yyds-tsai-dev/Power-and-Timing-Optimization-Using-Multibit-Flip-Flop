# Phase 3b 執行緒擴展研究(2026-07-11,server B)

**Type**: exp
**機器**: server B,4×Xeon Gold 6230(80 實體核/160 邏輯,4 NUMA),共用機。
**方法**: unified config(無 EVAL_ANCHOR,P1b 前 binary + Legalizer.h 修復),
`OMP_NUM_THREADS ∈ {8,16,32,64}`,串行階梯,首尾 8T 重跑量環境漂移,每輪記錄 loadavg。

## 核心結論

1. **分數對執行緒數完全不變**(最重要,de-risk 全部後續):
   - tc1:8/16/32/64 全部 `734,711,974.730639`(load ~150 窗口)
   - tc2:8/16/64/8 全部 `742,139.073150218`(load 27→92 混合窗口)
   - 兩案、兩種負載環境、一位不差。**軌跡由 accept 順序決定而 accept 順序
     不依賴執行緒切分**——跨機分數差異(tc2 本機 742,139 vs server A 723,165,
     +2.6%)來自 FP/toolchain 差異,與執行緒無關。
2. **tc2 wall 擴展曲線**(分數恆定,時間實測):

   | T | wall | CPU% | 加速比 |
   |---|---|---|---|
   | 8 | 19:41(安靜)/ 26:59(load 80)| ~710% | 1.0× |
   | 16 | 13:09 | 1250% | 1.5× |
   | 64 | **6:47** | 3015% | **2.9×**(且在 load 92 下!)|

   T64 有效吃到 ~30 核。**8 執行緒的歷史值在多核機器上白放 ~3× 速度**。
3. tc1 階梯(load ~150 污染)僅分數結論可信;乾淨 wall 曲線待機器安靜時補
   (T16 相對 T8 約砍半、T32/T64 受限於當時僅 ~7 閒核,無進一步增益——
   佐證「加速上限 = 可用核數」而非演算法瓶頸)。
4. 與 Phase 0 profiling 一致:barrier 空等 ~17% 意味 scaling 有天花板;
   de-hashing(3a-1)後 barrier 佔比預期上升,屆時重量 scaling 曲線。

## 撞牆案追加:T8 vs T64 同窗口對照(threads→score 判決)

| Case | T8 | T64 | Δ 分數 | wall |
|---|---|---|---|---|
| tc3 | 726,007,429.23(2566s)| 725,926,035.70(840s)| **−81,393(−0.011%)** | 3.05× |
| hc04 | 726,284,229.68(2601s)| 726,084,443.93(872s)| **−199,786(−0.028%)** | 2.98× |

**T64 在同一 1200s 預算內嚴格優於 Phase 0 的 3× 加時實驗**(tc3 −81k vs −54k;
hc04 −200k vs −39k),同時 wall 砍到 1/3——**時間預算制 + 更多執行緒 = 分數與
runtime 雙贏,無 trade-off**。機制:預算秒數內完成更多 exact 報價與 commit 輪次。
(不變性註記:不撞牆案分數逐位不變;撞牆案分數「隨工作量」變,方向實測為改善。)

## 對 unified config 的建議

- **執行緒數改為機器自適應**(如 `min(物理核, 32)`),分數零風險有實測背書;
  submission/正式紀錄仍可鎖 8T 保守值,但 2-min tier 與 Pareto 曲線
  (Phase 3 交付)應以高執行緒數跑——同 wall 預算下能做更多 exact 報價。
- 撞牆案(tc3/hc04/hc02-r1)的 1200s 預算在高執行緒下 = 更多工作量:
  **時間預算制 + 執行緒不變性 ⇒ 提高執行緒數會直接變成分數**(待 gate 級驗證)。
